The complete system design

End-user customization of a live web app — UI and business logic — under developer-declared invariants. Two planes, three trust zones, deterministic gates, fail-open everywhere.
grounded in the repo · sources: docs/INVARIANTS-PIPELINE.md + docs/ONBOARDING-PIPELINE.md + docs/DESIGN.md
01

Overview

Invariance lets end users of an existing web app customize it with natural-language prompts — both its look (tokens, styles, layout, slots) and its business logic at the API seam — while the app's developers stay in control through declared invariants. Two independent planes do this, and they answer the question "when is the change actually live?" in two different ways.

The one rule that makes it safe: the LLM is in the loop, never in the gate. The model only proposes; everything that is enforced is enforced by deterministic TypeScript + cryptography. Verification contains no LLM. Every failure path falls open to the base app.

Trust zones — who runs what

Three zones across a hard control-plane / data-plane boundary. The control plane (our infra) authors, verifies, signs and distributes. The data plane (the developer's own servers + the user's browser) only ever loads static, signed artifacts and verifies them locally.

END-USER BROWSER
data plane · runs developer-shipped code
  • client Customer web app — React+Tailwind, developer-shipped; components read var(--inv-*) tokens, regions wrapped in &lt;m.slot&gt;.
  • client @invariance/client (Tier-0): ModLoader (fetch→verify→cache bundle), UI overlay engine, prompt widget submitPrompt(), async telemetry.
  • client @invariance/design (look plane): CustomizationPanel + m.slots, Gatekeeper + Designer, compiler, verifyV2, apply → :root.
DEVELOPER INFRASTRUCTURE
data plane · customer-owned · stores nothing durably
  • server Frontend host — serves the app + bundled Invariance SDKs; holds no Invariance state.
  • server API server · @invariance/server (Tier-1): withInvariance/Express middleware, runtime (fetch pointer + verifyBundle), QuickJS-WASM sandbox, capability + field enforcement.
  • server Customer backend / DB — the real data hooks transform on the way out; untouched unless a mod is active.
INVARIANCE CONTROL PLANE
control plane · our infra
  • our cloud control-plane monolith (Hono+Postgres): Authoring (LLM + verifier-in-loop) · Verification (no LLM) · Registry (sign · publish · pointers · kill-switch · lazy-migrate) · Analytics · Design-config + Themes store.
  • our cloud Postgres — durable source of truth: manifests, mod revisions, pointers, prompts (PII), themes, events.
  • Next.js Console — manifest + Invariants surface, mods + kill switches, Guardrails, Themes/rollback.
CDN
shared static artifact store
  • Immutable, content-addressed signed bundles served at /bundles/:hash with cache-control: immutable.
  • Static — ours or mirrored into the customer’s bucket. Trust comes from the signature, not the host.
LLM
authoring brain
  • qwen2.5 via Ollama (OpenAI-compatible, default, no key) or Anthropic (opt-in).
  • Used only in authoring. Never in verification, never on the production request path.
No production request ever transits Invariance. The prod path is Browser ↔ Developer’s server ↔ CDN (static fetch + local signature check). Control-plane downtime can never break the customer app — distribution is a short-TTL mutable pointer ("active modset = hash X") in front of immutable signed bundles.

Where invariants are enforced
  • Compiler, not the LLM: allowed_modes/font_registry/locked_tokens violations throw; locked tokens are written last and override every computed value (compiler/compile.ts).
  • Contrast solved by OKLCH search; the developer floor can only raise the target.
  • verifyV2 (7 tests): all 38 tokens present · locked byte-identical · contrast floor · chroma cap · fonts in registry · all var(--inv-…) resolve (verify/compiled-tests.ts:391).
How it stays correct
  • Recompile-on-fail = Designer retry (max 2) — there is no path that relaxes a constraint or applies an unverified spec.
  • Goes live the instant root.style.setProperty(key,value) runs — pure CSS cascade, zero React re-render (runtime/apply.ts:34).
  • Live reconciliation: when the dev tightens an invariant, the applied theme is re-verified and recompiled-or-dropped, no reload (context/provider.tsx:162).

The novel half: authoring builds a verified, signed bundle (control plane); runtime executes it sandboxed, per request, on the customer’s server (data plane).

Verifier-in-the-loop (retry ≤3): failed reasons become feedback. The verifier rejects writes to immutable fields, dangerous CSS/HTML, illegal hooks (no eval/Function/globalThis/fetch…), and over-budget hooks. The user’s prompt is stored in ModRecord — never in the signed bundle (PII).

Defense in depth
  • Only status==='active' executes; {code("verifyBundle")} re-checks hash + signature + schema before any hook runs ({cite("packages/schema/src/signing.ts:69")}).
  • Per-hook capability bounding: checkCapabilityWrites discards any changed path not declared (packages/server/src/enforce.ts:19).
  • Immutable fields by multiset: reorder OK, any add/remove/rewrite → return the ORIGINAL payload (all-or-nothing).
The apply line
  • Kept only when the hook succeeded and capability check passed and field-constraint check passed: current = execution.result (packages/server/src/runtime.ts:226).
  • Any exception anywhere → original payload. Fail-open everywhere.
  • An already-verified bundle is cached by contentHash (immutable, so sound).
09

Distribution model

Two-step, so a kill-switch or supersession propagates within the pointer TTL while bundles stay cacheable forever.

Mutable side — pointer
  • Short-TTL (~5s) per-subject pointer: "active modset = hash X".
  • Manifest publish marks active mods stale (lazy migration); kill-switch flips disabled/active; superseded mods cannot flip.
  • Runtime fetches it with cache:'no-store' — a stale cache here once silently no-op’d all hooks.
Immutable side — bundle
  • ed25519-signed envelope over canonical JSON (sorted keys at every depth); contentHash = sha256(payload).
  • Served content-addressed with cache-control: immutable. New revisions supersede via the pointer.
  • Trust is in the signature → bundles can be mirrored into the customer’s own CDN.

Pointer status

StatusRuntime behavior
activeexecutes — the live modset for this subject
stalemanifest changed; base behavior until the next client session revalidates
degradedverification/migration downgraded it; base behavior, AI re-fix offered
disabledkill switch flipped; base behavior (superseded mods cannot flip)
noneno mod for this subject; base app
Developer release path: new manifest version → registry marks affected bindings stale → next user session revalidates → pass / degrade-to-base / offer AI re-fix. The prod path touches only static CDN artifacts + a local signature check.

Enforcement semantics

The same path / diff semantics run at verify-time (control plane) and run-time (data plane) — defense in depth. These are the rules both engines share.

Paths & diffs
  • diffPaths treats a pure array permutation as a write to the array itself, not its element fields — so "sort my list" mods are possible (paths.ts:64).
  • Immutable-field policies compare the multiset of values at the path: reordering is legal; rewriting/adding/hiding a protected value is not.
Write declarations
  • The verifier rejects declared writes targeting an immutable field (descendant-or-equal path) and whole-body writes on such endpoints — but allows strict-ancestor declarations (e.g. shows).
  • fields:undefined = whole-body write (allowed unless the endpoint has immutable fields); fields:[] = explicitly rejected.
  • statusCode ≥ 400 responses are never transformed; GET endpoints reject request-phase hooks.

Core invariants & sharp edges

System invariants

  • Runtimes execute only signed, verified Mod Bundles (verifyBundle before anything).
  • Bundles are immutable; new revisions supersede via the registry pointer.
  • User prompts never go into bundles (PII) — they live control-plane-side.
  • Verification is deterministic — no LLM in the verify step.
  • Hooks run sandboxed with hard budgets, touching only declared endpoints/fields.
  • Any fetch/verify failure fails open to base app behavior. The developer's infra stores nothing durably.

Sharp edges the trace surfaced

Signing-key durability
Without persisted INVARIANCE_SIGNING_*, keys regenerate on restart → every bundle fails verification → universal silent no-op. Open hand-off footgun.
Auto-repair widens writes
The final writes set is partly acorn-inferred; safety rests on the verifier’s immutable-field check running on the repaired bundle.
Two look-plane verifiers
THEME/SLOT_F1 use verifyV2 (7 tests); F2–F4 use the older v5 engine. Confirm overlap.
Kill-switch latency
A disabled mod can keep executing until the cached pointer expires (~5s).
One-shot drop warning
After warning once, a weak model is trusted to drop existing customizations (prevents non-convergence).
